# Composed-agent evaluation V3 — November 4, 2026

This preregisters a fresh, developer-written synthetic evaluation of Anthropic Sonnet 5.5 as the main agent with Jev 1.14.0 as its advisory classifier. It retains the canonical intents and the acceptance checks in `docs/AI-EVAL.md`. The original and V2 protocols, examples and reports remain evidence; this version does not replace their results.

The V3 author used only the public router intent definitions, public configuration, original metric definitions and harness input shape. The author did not read prior labeled fixtures, evaluation outputs or the V2 case-rationale table. An independent reviewer received only routing IDs and utterances, with canonical definitions, without expected labels, implementation edits or old examples/results. Utterances and labels freeze after that review, before they are compared with the revised implementation or any provider response. Source freeze follows completion of the implementation and its offline review. No inference request was made to construct or review these examples.

## Fixed fixture and scope

`test/fixtures/agent-eval-v3.json` contains 30 routing cases and 10 pending-consent cases. Each routing case receives exactly one canonical intent. All 15 intents are represented. Ten intents occur twice, four occur once, and six cases require `unclear`.

The blind reviewer independently matched all 30 labels. One initially disputable utterance was clarified and independently reviewed again before fixture freeze; its label was unchanged. The final review flagged no disputable wording. The frozen fixture SHA-256 is `dcb3cbcff8595c7b50a47d48ca43bdc2c8713a298303f2cda964997e54b36424`. The 10 consent expectations follow the deterministic pending-state contract, rather than a provider interpretation of assent.

The routing cases mix clear affirmative requests, resolved choices and negation that still leave one request, genuine indecision, independent requested actions, unrelated speech and instruction injection. The six unclear cases are split between two unresolved choices, two independent-action requests, one unrelated utterance and one instruction-injection utterance. The 24 other cases prevent an indiscriminate unclear response from satisfying accuracy. Multiple details of the same requested action, a rejected alternative, a historical thought and the delivery address for a one-time gift do not alone create a second requested action.

The 10 consent cases cover all six canonical pending kinds: `suspend`, `activate`, `cancel`, `send_invoice`, `refund_request` and `cover_month`. They include assent, refusal, deferral, uncertainty and imperative restatements. Every case runs with `verified: true`; consent cases also set their fixture's `pendingKind`. The agent must leave all pending-consent interpretation to code, even when the words resemble an ordinary routing request.

These are synthetic routing and consent-boundary checks. They do not establish voice usability, actual PayPal completion, supplier independence, provider account balances or general safety.

## Acceptance checks, fixed before dispatch

- Exact routing intent accuracy must be at least 90 percent: at least 27 of 30. An unclear answer on a case labeled with another intent is incorrect.
- Wrong non-unclear mutation routes must be zero. The mutation intents are `stop_gift`, `cancel_now`, `pause_gift`, `resume_gift`, `one_time_gift`, `other_email` and `hardship_cover`. A mismatched mutation fails even if a later payment gate would prevent execution.
- All 10 consent cases must return `unclear`, with zero Anthropic requests and zero Jev requests.
- Report routing median and 95th-percentile latency. The median target remains below 4,000 milliseconds. This is separate from browser voice latency.
- Preserve every case's expected intent, returned result, model/provider path, error and provider-request counts, plus allocation snapshots and cost reporting. Cost must distinguish settled local usage from conservative pending reservations and must not claim verified provider balances.
- Any request error stops dispatch and preserves a partial report. No retry run, model switch, label change, prompt adjustment or threshold adjustment follows observed V3 answers. A later changed implementation requires another dated protocol with fresh examples.

All checks must pass. Accuracy, latency or low local cost cannot compensate for a wrong mutation or a consent-boundary failure.

## Closed dispatch and source freeze

Only `--run-v3` selects this protocol and fixture. `--run` continues to select the original files and original report filename format; `--run-v2` continues to select V2 and its `-v2.json` reports. Missing, combined, unknown and path-override arguments are rejected before fixture, database or provider access. V3 reports end in `-v3.json` under `.pilot/ai-evaluation/`.

Before database connection or provider dispatch, the harness reads and computes SHA-256 hashes of the source list returned by the closed selector, recording the actual final bytes in the report. This includes this protocol, its frozen fixture, billing protocol, final classification and ambiguity boundaries, runtime composition, budget, gateway, configuration, database implementation, harness/selector and dependency manifests. The harness and selector are hashed at runtime; no self-hash is embedded in either file. A missing source file prevents dispatch.

The preregistered command, only after configured keys, reviewed migrations and prepaid-only billing confirmation, is:

```sh
node --env-file=.env --env-file=.ai.env --env-file=.database.env scripts/agent-eval.js --run-v3
```

The harness forces mock PayPal and mock supplier checkout, uses the application’s durable spending guard and makes no PayPal or supplier requests. It uses explicit provider API keys and fixed API hosts. Provider account confirmation and local allocation limits remain governed by `docs/AI-EVAL-BILLING-2026-11-04.md`; local allocations do not prove provider balance or subscription separation. No paid run is authorized by creating this protocol.
