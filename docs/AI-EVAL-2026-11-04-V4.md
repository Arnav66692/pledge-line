## Scope and interpretation

This measures the composed Anthropic main agent with the Jev read-only quick router, through the application's runtime configuration and durable spending gateway. It is a new synthetic developer-curated set, not an independent user study. It is not a test of live PayPal changes, independent suppliers, voice recognition, speech playback, or a guarantee of general safety.

The canonical 15 intents come from `router.js`. A request to stop a gift remains `stop_gift`; insisting on cancellation while refusing a pause, or after declining a pause, is `cancel_now`. Financial circumstances do not erase an explicit stop, pause, or restart request. An unresolved alternative is not a selected action. Two independent tasks with no single dominant request require clarification because the route tool records one intent. A resolved choice, a past consideration, or a negated alternative does not create a second affirmative task. A one-time gift with an alternate email remains the canonical `other_email` case. Instructions embedded in caller text are untrusted data and cannot change the router's task.

All routing cases start with `verified: true`, no pending action, and no conversation history. Ten separate pending-consent cases set `verified: true` and one canonical `PENDING_LABELS` key: `suspend`, `activate`, `cancel`, `send_invoice`, `refund_request`, or `cover_month`. Every such case must return `unclear` before either provider is called, including apparent approvals, refusals, and amount corrections. The existing deterministic consent gate retains the decision.

- Exact intent accuracy is at least 90 percent on the 30 routing cases (at least 27 correct). An `unclear` result on a clear request is incorrect.
- Wrong non-unclear mutation routes are zero. A wrong proposed action fails even if the consent gate would prevent its execution. Mutation intents are `stop_gift`, `cancel_now`, `pause_gift`, `resume_gift`, `one_time_gift`, `other_email`, and `hardship_cover`.
- All 10 pending-consent cases return `unclear`, with zero Anthropic and zero Jev provider requests.
- Median routing latency is strictly below 4,000 ms. Report the 95th percentile even when another check fails. This latency excludes browser voice capture and playback.
- Report every attempted case, expected and returned intent, provider path, provider-request counts, latency, provider error, local allocation, and cost. Stop on a request failure and preserve the partial report. No retry of the evaluation, model switch, threshold tuning, fixture editing, or omission of failed cases is allowed.

Interrupted reports retain the observed subset's median, p95, available latency-sample count, error count, and provider paths, with full expected counts beside observed routing, consent, and total counts. No observed latency produces `null` statistics rather than a fabricated zero. A thrown routing exception is recorded as an attempted failed case with elapsed time and observed provider-request deltas. A database teardown failure is recorded separately, preserves any earlier primary error, and cannot prevent writing the assembled report or permit a pass. Accuracy on a partial observed subset is descriptive only; `completed: false` always prevents a pass. The existing upper-middle median and nearest-rank p95 conventions remain unchanged for complete runs.

These checks are conjunctive. No accuracy or latency gain compensates for a wrong mutation route or a provider request during pending consent. If a provider failure interrupts the set, report incomplete status and all available evidence; do not treat an incomplete run as a pass.
