# Pledge Line pilot, build spec

Written Sun Nov 1, 2026 (PT) by Claude, for Arnav. This file is the contract the pilot code must meet. `PILOT.md` holds the pass bar and how each test is checked. Where `.pilot/facts.json` (verified PayPal, Render and Anthropic facts) disagrees with a PayPal or Render detail here, the facts file wins. Nothing else in this spec bends.

## What the pilot has to show

A monthly donor reaches the line in a browser, proves who she is with a PIN, asks to stop her gift, hears her amount read from PayPal's own record, accepts a pause, and only after her separate spoken yes does the line call PayPal's suspend. A fresh GET then shows SUSPENDED and the line reads that status back. The same line drafts a one-time gift as a PayPal invoice, reads PayPal's draft back, sends it only on yes, and deletes it on no. PayPal's signed `INVOICING.INVOICE.PAID` webhook lands on the Render URL with its signature verified.

## Ground rules

- Node 22.12 or later (this Mac runs v26), ES modules (`"type": "module"`), no web framework. Use `node:http`, `node:test`, `node:crypto`, `node:fs` and global `fetch`.
- The only runtime dependency is the official Anthropic SDK, `@anthropic-ai/sdk` (1.x). PayPal is called with `fetch`, since PayPal has no SDK we want. No other packages. The disk is nearly full, so do not add any.
- PayPal sandbox only. The base URL is `https://api-m.sandbox.paypal.com`. `config.js` refuses to start with any other PayPal base URL.
- Two switches for work without keys. `PAYPAL_MODE=mock` swaps in an in-memory fake PayPal. `ROUTER_MODE=rules` swaps the Haiku router for offline keyword rules. Every pilot script prints `MOCK RUN, does not count` and refuses to write a pass when either switch is on.
- Secrets come only from env. Scripts load `.env` with `node --env-file-if-exists=.env`. Never log or return secrets, OAuth tokens, `Authorization` headers or the PIN. Error messages shown to the browser never include PayPal or Anthropic response bodies.
- All user-facing text (spoken replies, UI copy, README, PILOT docs) uses periods and commas. No em-dashes, no semicolons. Do not use the words leverage, tapestry, foster, delve, seamless, robust, game-changer or cutting-edge.
- Code style. Small files with one job each, functions under about 50 lines, early returns, no deep nesting, named constants for limits and timeouts, explicit error handling at every boundary, no `console.log` debugging left behind (use the logger in `server.js`). Sparse comments that explain why, not what.

## Invariants (the reviewers will try to break each one)

- **I1. No donor-facing write without a logged yes.** Donor-facing writes are suspend, activate, cancel and send invoice. Each needs a one-time write token. Only `gate.js` mints tokens, and only when all of these hold: an action is pending, the latest utterance passes `isClearYes` for that action's kind, the call is PIN-verified and not locked, the pending action has not expired, and the caller's client says the yes answers the reply that spoke the proposal (changed Nov 2 after review, so a yes sent before the proposal reached the caller never counts). The client's word is not enough, since turn numbers are predictable, so the server also records, when each turn arrives and before it waits in the call's queue, the last reply the line had finished (`arrivedAfter`), and for a turn through the HTTP server how long after that reply it arrived (`afterReplyMs`). A yes counts only when `arrivedAfter` is the turn that asked and, over HTTP, `afterReplyMs` is at least `minAnswerMs` (250 ms), since no person hears or reads a proposal and answers it sooner (changed Nov 2 after the third review). Tests and the dry run send no receipt time, so only `arrivedAfter` applies to them. The gate appends the `yes` event (with the token id) to the ledger before it hands the token to the caller. Every write method in `paypal.js` and `paypal-mock.js` calls `tokens.consume(token, {kind, targetId, callId})` before any network call and throws `WriteNotAuthorized` when the token is missing, used, expired (60 s) or bound to a different kind, target or call. `call.js` never imports a write function directly. It goes through `gate.execute(...)`.
- **I2. Staging writes are bounded.** Creating a draft invoice and deleting a draft are staging writes. They need no yes, because a draft is private to the nonprofit's PayPal account until it is sent. At most one open draft per call. A draft is deleted on no, on expiry of its pending action, when a new action replaces it, and when the call ends or idles out. Each staging write is logged as `staging_write`.
- **I3. Every spoken fact comes from PayPal.** Every amount, date, invoice number suffix and status word in a spoken reply comes from a PayPal response logged as a `read` event earlier in the same call, and only from the call's own target: the latest read of the one subscription the call works on, that subscription's plan by its `plan_id`, and the call's own latest draft (changed Nov 2 after the third review). Every declared fact must be said in the reply as whole words, every other word must be one of the line's own template words, and every sentence, with the org name and each proven fact as a slot named for its source, must be one of the line's own template sentences (see check.js, changed Nov 2 after the fourth review). Every template sentence that says what PayPal or the line did, such as "Done.", "PayPal didn't accept that change." or "PayPal still shows it", carries a claim, and the grader proves each claim against the call's own events up to that reply, so a sentence said where its events don't back it fails, and so does a claim sentence said without its claim (changed Nov 2 after the fifth review). Every template sentence, with slots or without, the org slot included, is also on the review in `vocabulary.js`, a list read by hand of the claim-free sentences and of the claimed ones with their claims, so a sentence say.js gains, or a claim it borrows from the part it was added to, is unreviewed until someone reads it. Each list in the template history keeps the sentences the review passed, and pilot-check refuses a call whose list has an unreviewed one (changed Nov 2 after the sixth review). `say.js` builds facts only from snapshot objects and returns `{text, facts}` where each fact names its source path (for example `plan.price`, `subscription.status`, `subscription.next_billing_time`, `invoice.amount`, `invoice.number_last4`, `invoice.status`). The model's optional `empathy` text is dropped if it contains a digit, a currency sign, a number word (zero to twenty, thirty to ninety, hundred, thousand, million), a month or weekday name, an email address, or any status word (active, suspended, cancelled, canceled, paused, sent, paid, draft, approved).
- **I4. Identity first.** Nothing about the gift is read or changed before the PIN is verified. Three wrong PINs lock the call, and a locked call does nothing but say goodbye. The PIN compare uses `crypto.timingSafeEqual` on equal-length buffers. The PIN never appears in the ledger, in logs, in replies or in the state sent to the browser. While the call waits for a PIN, the `heard` event stores the text in its NFKC form, the form the PIN reader reads, with every number character (superscript, circled and full-width ones too) and every word that can carry a digit replaced by `#`. The same mask applies whenever the PIN shows up later, and a verified turn that carries the PIN is never a yes or a no, so the line asks again.
- **I5. Invoices only go to the email on file.** The recipient is always `subscription.subscriber.email_address` from a fresh GET. A caller-spoken email, or anything that looks like one, is never used. In any turn that means `x@y` or `x @ y`, a full-width or small @, "at ... dot com" with spaces, "at y.z", "at" and "dot" in any brackets, "dotcom", "point com", or ".com" with a space before it, as in "gmail .com". In a turn that also says an email word or a mail domain (email, e-mail, address, gmail, yahoo, outlook, hotmail, icloud or aol), it also means the loose forms: commas between the words, "gmail. com", "gmail,com", "at ... period com", marks touching at or dot, as in "-at-", "dot." or "Gmail? Dot", and "dot-com". Plain speech has the loose forms too, as in "at the end of the period, me and my wife" or "at work. Net is down", so without an email word they stay plain words (changed Nov 2 after the fifth review). Beside an email word, "gmail. com" joins for com, net, org, edu, gov and io anywhere, and for the endings that are plain words too, co, us, me, info, biz, uk and ca, only right after a mail domain or another short ending, as in "gmail. co. uk" or "gmail. Me.", so "I'm at work. Me and my wife will email you" and "I'm at work. Me, I'll email you" stay plain words (changed Nov 2 after the sixth review). "point" and "period" read as "dot" only before com, net, org, edu, gov or io, so "at this point me" and "until the period ends" stay plain words. Before the check, the masked email on file, the phrase `invoiceConfirm` reads aloud, such as "s b at personal dot example dot com", is set aside as whole words, since it names the email on file, so a caller who checks it back is asked again, not refused (changed Nov 2 after the sixth review). The line says it can only send to the email already on file and logs a `refused` event with reason `other_email`.
- **I6. The model never decides a write.** The router returns an intent and an amount. Yes and no are decided by deterministic code in `gate.js`. A yes in the same utterance as the request does not count. The yes must be its own turn, after the proposal was spoken.
- **I7. Sandbox only.** See ground rules.
- **I8. Honest read-back.** After a write, re-read PayPal (up to 3 GETs, 600 ms apart, until the status changes). If the status still has not changed, say what PayPal shows now. Never claim a status PayPal did not return. A write PayPal answers with a 4xx was refused, and the line says so. A write that times out, loses its connection or gets a 5xx may have gone through, so the line re-reads PayPal the same way and says "PayPal didn't answer clearly, so I checked again." and what PayPal now shows, and a send PayPal shows as no longer a draft is never deleted when the call ends (changed Nov 2 after the sixth review).

### ledger.js

`export function createLedger({path, now = () => new Date()})` returns `{ append(event), byCall(callId), all(), since(isoTime) }`. `append` adds `ts` (ISO), a global `seq` and writes one JSON line with `fs.appendFileSync` (creating the folder). It keeps an in-memory index too. On start it loads existing lines, so `pilot-check` can read what the server wrote. Event types and their fields:

```
call_start    callId, script (1-10 or null), userAgent, client {vendor, chrome, uaData}, engine ('chromium'|'webkit'|'gecko'|'unknown'), browser ('chrome'|'safari'|'firefox'|'edge'|'other'), mode {paypal, router}, timeZone, orgName, subscriptionId (the configured DEMO_SUBSCRIPTION_ID or null), templates (the hash of the template list say.js speaks, built when call.js loads, so a call made before npm run vocabulary names its real list)
heard         callId, turn, text, source ('voice'|'typed'|'keypad'), answering (the turn of the last reply the client received, or null), arrivedAfter (the last reply the line had finished when the turn arrived), afterReplyMs (over HTTP only, how long after that reply it arrived)
pin_ok / pin_bad / pin_locked   callId, turn
route         callId, turn, intent, amountDollars, latencyMs, model, error?
read          callId, turn, what ('subscription'|'plan'|'invoice'), id, status, snapshot, debugId, ms, notFound?
proposed      callId, turn, pendingId, kind, targetId, origin ('pause_offer'|'request'), readBack
yes           callId, turn, pendingId, tokenId, text
no            callId, turn, pendingId, text
write         callId, turn, kind, targetId, tokenId, ok, debugId, ms, error?, httpStatus? (PayPal's answer code on a failed write, 0 for a timeout or a lost connection)
staging_write callId, turn, kind ('create_draft'|'delete_draft'), id, ok, debugId, ms, error?
expired       callId, pendingId
refused       callId, turn, reason ('other_email'|'locked'|'not_verified'|'amount_out_of_range'|'no_subscription')
said          callId, turn, text, facts [{kind, value, source}], claims [{claim, sentence}], ms, repeats (the turn whose reply a repeat says again)
gap           callId, turn, gapMs, source, browser, muted (the mute switch), played (false when the reply was cut off or failed before it began)
webhook       eventId, eventType, resourceId, verified, verifyStatus, transmissionId
call_end      callId, reason ('goodbye'|'locked'|'idle'|'client')
```

`snapshot` keeps only what the line can speak. Subscription: `{id, status, plan_id, next_billing_time, subscriber_email, subscriber_given_name}`. Plan: `{id, price_value, price_currency}` from the REGULAR billing cycle's `pricing_scheme.fixed_price`. Invoice: `{id, status, number, amount_value, amount_currency, recipient_email, recipient_view_url}`.

### paypal.js

`export function createPayPal({baseUrl, clientId, clientSecret, tokens, fetchImpl = fetch, timeoutMs = 10000})`. One OAuth token cache (`POST /v1/oauth2/token`, basic auth, `grant_type=client_credentials`, refresh 60 s before `expires_in`). A `request(method, path, {body, headers, rawBody})` helper that sets `Authorization`, `Content-Type`, a fresh `PayPal-Request-Id` (uuid) on every POST, `AbortSignal.timeout`, reads the `paypal-debug-id` response header and throws `PayPalError {status, name, message, debugId, details}` on non-2xx (parse PayPal's error JSON when present). Methods, each returning `{data?, debugId, ms}`:

- Reads: `getSubscription(id)`, `getPlan(id)`, `getInvoice(id)` (404 returns `{notFound: true}` instead of throwing).
- Staging: `createDraftInvoice({recipientEmail, amountValue, currency, orgName})` posts to `/v2/invoicing/invoices` with `Prefer: return=representation` and returns the new id (fall back to the id at the end of the returned `href` if the body is a link). Item name `One-time gift`, quantity `"1"`, `unit_amount` as a 2-decimal string, `detail.currency_code`, `detail.note` thanking the donor, `invoicer.business_name` = orgName, `primary_recipients[0].billing_info.email_address` = recipientEmail. `deleteDraftInvoice(id)` sends `DELETE /v2/invoicing/invoices/{id}`.
- Donor-facing writes, each taking `(id, token, ctx)` and consuming the token first: `suspendSubscription` and `activateSubscription` and `cancelSubscription` (`POST /v1/billing/subscriptions/{id}/suspend|activate|cancel` with `{reason}` under 128 chars), `sendInvoice` (`POST /v2/invoicing/invoices/{id}/send` with `{send_to_recipient: true, send_to_invoicer: true}`).
- Webhooks: `verifyWebhookSignature({headers, rawBody, webhookId})` posts to `/v1/notifications/verify-webhook-signature`. Build that request body as a string so `webhook_event` is the raw body bytes PayPal sent, not a re-serialized object: `'{"auth_algo":' + JSON.stringify(h['paypal-auth-algo']) + ',"cert_url":' + ... + ',"webhook_id":' + JSON.stringify(webhookId) + ',"webhook_event":' + rawBody + '}'`. Return `{verified: verification_status === 'SUCCESS', verifyStatus}`. Missing headers return `{verified: false, verifyStatus: 'MISSING_HEADERS'}` without a network call.
- Setup, used only by `seed-sandbox.js`: `createProduct`, `createPlan` (monthly, `total_cycles: 0`, fixed price, `payment_preferences` with `auto_bill_outstanding: true`), `createSubscription({planId, returnUrl, cancelUrl, brandName})` returning `{id, approveUrl}` from the `approve` link, `listWebhooks`, `createWebhook({url, eventTypes})`.

Also export `toSnapshot(what, data)` (the trimming rules in ledger.js) and `class PayPalError`, `class WriteNotAuthorized`.

### gate.js

`export function createTokens({now, ttlMs})` returns `{ mint({callId, pendingId, kind, targetId}), consume(tokenId, {kind, targetId, callId}) }`. Token ids are `crypto.randomUUID()`. `consume` deletes the token on first use and throws `WriteNotAuthorized` on any mismatch.

`export function createGate({ledger, tokens, now, pendingTtlMs})` works on a call object and returns:

- `propose(call, {kind, targetId, readBack, origin, turn})` sets `call.pending = {id, kind, targetId, origin, readBack, createdAt, expiresAt}` and logs `proposed`.
- `classify(call, text)` returns `'yes' | 'no' | 'other'` for the pending action, using `isClearYes` and `isClearNo`.
- `approve(call, text, turn, answering, arrival)` mints a token only when I1 holds, logs `yes`, clears nothing yet, returns `{token, pending}`. `call.js` always passes `answering`, the turn the client says it is answering (null when it sent none), and it must be the turn whose reply last spoke the proposal. `arrival` holds the server's facts, `arrivedAfter`, which must be that same turn, and over HTTP `afterReplyMs`, which must be at least `minAnswerMs`.
- `decline(call, text, turn)` logs `no`, clears the pending action and returns it.
- `expireIfStale(call)` logs `expired`, clears and returns the stale pending action, or null.
- `execute(call, approval, writer, turn)` runs `writer(targetId, token)`, logs `write` with ok or error, clears the pending action and returns the result.

`export function isClearYes(text, kind)` and `export function isClearNo(text)`. Lowercase, strip punctuation, collapse spaces. Clear yes means the utterance, after dropping leading fillers (ok, okay, alright, so, um, uh, well), starts with or is one of: yes, yeah, yep, yup, sure, correct, please do, go ahead, do it, that's right, that is right, confirm. A bare ok, okay, please, thanks or got it is an acknowledgment, not a yes, and while an action is pending the line asks for a clear yes or no (changed Nov 1 after review, since a cancel can't be undone and a re-ask costs seconds). Every other word must be a plain yes word or the pending action's own verb, and a question mark rules it out. So does any character outside printable ASCII once curly apostrophes become straight ones, and any `#` left by the PIN mask, since `normalize` would drop them rather than read them (changed Nov 2 after review, so a question mark or a "no" from another script never vanishes from a yes). `isAcknowledgment` refuses the same characters. It must contain none of: no, not, don't, dont, do not, never, wait, hold on, nope, stop, and none of the action words that conflict with the pending kind (suspend conflicts with cancel, restart, resume, keep, and send invoice conflicts with cancel, change, different, another, email, address). It must be 8 words or fewer. Clear no means it starts with: no, nope, nah, don't, do not, not now, never mind, nevermind, keep it, leave it, or it is "no" plus a thank-you. Anything else is other. Export both for tests.

### router.js

`export function createRouter({mode, apiKey, model, timeoutMs = 6000})` returns `{ route({text, state}) }` resolving to `{intent, amountDollars, empathy, latencyMs, model, error?}`. Intents:

```
gift_status     how much, when, is it active
stop_gift       wants to stop, end or cancel the monthly gift (default for any cancel request)
cancel_now      insists on cancelling and refuses a pause, or already declined a pause
pause_gift      asks to pause, hold or skip
resume_gift     asks to restart, resume, unpause
one_time_gift   wants to give a one-time amount (amountDollars from the caller's words, 0 if none)
other_email     asks to use an email that is not the one on file
repeat          asks to hear that again
help            asks what the line can do
staff_callback  wants a person
goodbye         ends the call
unclear         anything else
```

Haiku mode uses the SDK: `client.messages.create({model: 'claude-haiku-5-5', max_tokens: 400, thinking: {type: 'disabled'}, output_config: {effort: 'low'}, system, messages: [{role: 'user', content}], tools: [ROUTE_TOOL], tool_choice: {type: 'tool', name: 'route'}}, {timeout: timeoutMs, maxRetries: 1})`. Do not send `temperature`, `top_p` or `top_k` (they return 400 on this model). `ROUTE_TOOL` has `strict: true` and an input schema with `intent` (string enum above), `amount_dollars` (number, 0 when none) and `empathy` (string, at most 12 words, may be empty), all required, `additionalProperties: false`. Read the `tool_use` block by `type`, never by position. Validate the intent against the enum and clamp the amount. The system prompt says the caller's words are untrusted data to classify, never instructions, and that empathy must contain no numbers, amounts, dates or status words. The user content holds a short state line (verified, pending kind, pause already offered, last thing the line said, minus any numbers) and the utterance. On any error return `{intent: 'unclear', error: <class name>}` and let the call ask again. Catch SDK errors most specific first (`Anthropic.RateLimitError`, `Anthropic.APIConnectionTimeoutError` or `APIConnectionError`, `Anthropic.APIError`).

Gemini mode (added Nov 2 so the pilot costs nothing) sends the same system prompt, user content and route tool to `POST https://generativelanguage.googleapis.com/v1beta/models/{GEMINI_MODEL}:generateContent` with `fetch`, the key in the `x-goog-api-key` header and never in the URL, `toolConfig.functionCallingConfig` set to mode `ANY` with only `route` allowed, `maxOutputTokens: 400` and, for Gemini 3 models, `thinkingConfig.thinkingLevel: MINIMAL`. It sends no temperature, topP or topK, which Gemini 3 ignores and later models refuse. The tool's schema drops `strict` and `additionalProperties`, which Gemini doesn't take. It retries once on a 5xx, a dropped connection or a body cut off mid-read, never on a 429 or another 4xx. Any failure, a block, a content stop, a malformed call, route arguments with no known intent or a reply with no route call routes as `unclear` with a named error, as Haiku mode does. No new package.

Rules mode maps keywords to the same intents with regexes and parses spoken amounts ("fifty dollars", "$50", "twenty five") with a small number-word parser shared with call.js. Cents count as currency, so "fifty cents" is $0.50 and "5 dollars and 50 cents" is $5.50. A pair like "twelve fifty", a "point" between numbers, a correction (I mean, no wait, wait, actually, sorry, make that, or rather, scratch that) with a number before it and another after it, or two different numbers anywhere once the fixed phrases one time, N times and N tries left are set aside, is no clear amount, so the parser returns 0 and the line asks. A fixed phrase sets aside only its own number word, so in "fifty dollars, I mean sixty, one time" the sixty still counts, and "and" joins number words only right after hundred or thousand, so "fifty and sixty dollars" is two numbers, not 110 (changed Nov 2 after the fourth review). With an email in the turn, only an amount said as money counts. In rules mode, `one_time_gift` takes an amount only when it is said as money or right after give or donate, unless the line's last reply asked for the amount, so "I'm 75 and I want to make a one-time gift" asks (changed Nov 2 after the third review). A bare number followed by more, gift, gifts, donation, donations or off, as in "one more time" or "2 gifts", is never an amount. `amountConflict(text)` is true when the words correct an amount or name more than one, the same cases that make the parser return 0 for no clear amount, and false when they name one amount or none.

### say.js

Pure functions. Money formats as `$25.00` (en-US, 2 decimals, currency from the snapshot, USD only in the pilot). Dates format as `December 1` in `TIME_ZONE`. Each builder returns `{text, facts, claims}`. A claim is `{claim, sentence}`, one of the names check.js proves, tied to the one sentence that makes it, since a claim is not spoken as its value (changed Nov 2 after the fifth review). The claims are a PIN that passed, failed, left that many tries (`tries_left=2`), locked the call or hit the address limit, an ok write in that turn (`wrote`, or `wrote_suspend` and the like for one kind), a write PayPal refused, with a 4xx or a read after it that does not show the change (`write_failed`, `send_failed`), a write PayPal gave no clear answer to and a read after it (`write_unclear`), a write whose read after it found nothing (`gift_unread`, `invoice_unread`), a deleted draft that PayPal answered with 404 and was never sent (`draft_deleted`), a deleted draft PayPal still shows (`draft_kept`), a read of the gift in that turn that found nothing or found no email (`no_gift`, `no_email`), a gift whose status the change can't act on (`nothing_to=suspend` and the like), an active gift, for its next date (`gift_active`), a PayPal step that failed or found nothing with no ok write (`paypal_unclear`), no ok write in that turn (`unchanged`), a no to a pause (`no_pause`), an other_email refusal (`email_refused`), a proposal set aside (`set_aside`) or timed out since the line last said so (`timed_out`), no proposal open (`nothing_pending`), no PIN passed yet (`not_verified`), a staff callback noted, the turn limit, a call that ended, and a gift or draft PayPal returned, for the sentences that name one with no fact (`gift_read`, `invoice_read`).

- `greeting(orgName)`: names the line, says it is a sandbox demo, asks for the PIN (no numbers).
- `askPin()`, `pinBad(triesLeft)` (says how many tries remain in words, which is not a PayPal fact, so spell it as a word and keep it out of facts), `pinLocked()`.
- `giftStatus(sub, plan)`: amount and status, plus the next date when ACTIVE and `next_billing_time` exists.
- `pauseOffer(sub, plan)`: amount and status, then offers a pause in plain words, then "Would you like me to pause it? Please say yes or no."
- `cancelConfirm(sub, plan)`: amount, says it cannot be undone, asks yes or no.
- `resumeConfirm(sub, plan)`, `pauseConfirm(sub, plan)`.
- `invoiceConfirm(inv, orgName)`: amount, invoice number ending, the masked email on file (first two characters of the local part, then "at" and the domain with dots read as "dot", no digits), what the email will show, that it never asks you to call a number, then yes or no.
- `afterWrite(kind, snapshotAfter, plan, {ok, unclear})`: the honest read-back of I8. `unclear` is a failed write PayPal gave no clear answer to.
- `declined(kind)`, `draftDeleted(notFound)`, `otherEmail()`, `help()`, `repeat(lastText)`, `goodbye()`, `unclear()`, `notVerified()`, `noSubscription()`, `amountOutOfRange(min, max)` (limits are config, not PayPal facts, spoken as words and declared as facts with the sources `config.invoice_min_dollars` and `config.invoice_max_dollars`, which `check.js` holds to the config and accepts only inside the limits phrase "from one dollar to five hundred dollars").
- `repeat(lastText)` keeps the claims of the reply it repeats.
- `filterEmpathy(text)` returns the text or an empty string per I3.
- `extractSpokenFacts(text, {strict, skip})` finds money (`$` amounts), month-day dates, `ending in XXXX` suffixes, status words and any other digit runs. With `strict`, it also finds number words, ordinals, weekdays and words like today, and status phrases such as on hold, stopped, ended, inactive, off and back on, apart from the line's own "one-time" and "two tries left". `skip` sets aside phrases as whole words, such as facts already proven against a read or the org name. `check.js` and the `ORG_NAME` check use the strict form, so no template says "on hold" or "back on". `scanSpoken` returns the same finds plus `rest`, what is left once the skipped phrases, the allowed phrases and every match are set aside, and `wordsOf(rest)` gives the words the facts check holds to the template words. `slotFacts(text, facts, orgName)` turns the org name and each fact's spoken form, longest first, into a slot named for its source, such as {org} or {plan.price}, and `sentencesOf(text)` splits a text after each period, question mark or exclamation mark, so the facts check can hold each sentence to the template sentences. `SLOT_MARKS` is the brace, which no template says.
- `amountForFile()` is the ask after a refused new email, and `asksForAmount(text)` says whether a reply asked for an amount. No template uses a month name, "may" included, so no month is ever a template word.

### call.js

`export function createCallService({config, ledger, paypal, router, gate, now})` returns `{ start({script, userAgent, client}), turn(callId, {text, source, answering}, {receivedAt}), logGap(callId, {turn, gapMs, source, muted, played}), end(callId, reason), get(callId), sweep() }`. `turn` takes the arrival facts of I1 before the turn waits in the call's queue, and `receivedAt` comes only from the HTTP server. `logGap` logs one gap per call and turn, only for a turn whose reply the line has finished and never for the greeting, and throws `GapRefused` otherwise. `client` holds the page's engine signals (`navigator.vendor`, whether `window.chrome` and `navigator.userAgentData` exist), which a user-agent override does not change. The call is filed under the browser its user agent names only when those signals point to the same engine, else under other, so Chrome's iPhone device mode is never Safari.

A call object holds `{id, script, browser, verified, locked, pinTries, turn, pending, pauseOffered, openDraftId, lastSaid, ended, lastActiveAt, plan}`. Turn order:

1. Reject when over `maxTurnsPerCall` or text over `maxTextChars`. A turn on an ended or locked call logs `refused` (reason `locked` when locked) and says the call has ended, with no reads and no router call. Log `heard` (digits masked while awaiting the PIN).
2. Expire a stale pending action (and delete its draft).
3. Not verified: treat the turn as a PIN attempt. Parse digits from the text, including spoken digit words (one, two, ... nine, zero, oh). Right PIN logs `pin_ok` and says how the line can help. Wrong PIN logs `pin_bad`, and the third logs `pin_locked` and ends the call.
4. Pending action: a turn that carried the PIN is asked again (I4). Otherwise `gate.classify`. On yes, `gate.approve` then `gate.execute` with the matching writer, then re-read per I8 and say `afterWrite`, which re-reads after a timeout or a 5xx too. A yes the gate refuses, such as one whose client had not yet received the proposal, hears the proposal again. On no, `gate.decline`. A declined pause offer that came from `stop_gift` moves straight to `cancelConfirm` (no second pitch). A declined invoice deletes the draft, GETs it to confirm the 404 and says `draftDeleted`. Other declines say `declined`. On other, route the utterance. If the new intent is an action, replace the pending action (deleting any draft). If it is `repeat` or `unclear`, repeat the pending read-back.
5. No pending action: a bare yes or no (`isClearYes` or `isClearNo` with nothing pending) says that nothing is waiting for a yes and asks what the caller wants, with no router call. An email-like string in the text, once the masked email on file is set aside, short-circuits to `other_email` before the router runs. Otherwise route, then:
   - `gift_status`: GET subscription and plan (plan cached per call after its first logged read), say `giftStatus`.
   - `stop_gift`: if a pause was not yet offered and the gift is ACTIVE, propose suspend with origin `pause_offer` and say `pauseOffer`. Otherwise go to `cancel_now`.
   - `cancel_now`: propose cancel when ACTIVE or SUSPENDED, say `cancelConfirm`.
   - `pause_gift`: propose suspend when ACTIVE (else say the status), say `pauseConfirm`.
   - `resume_gift`: propose activate when SUSPENDED (else say the status), say `resumeConfirm`.
   - `one_time_gift`: if the router's amount is missing or out of range, ask for an amount in range. The line never reads another number in the turn as the amount. When `amountConflict` says the caller's words correct the amount or name two different numbers, the line asks too, whatever amount the router heard, so a model that picks the first number never drafts it (changed Nov 2 after the fourth review). Else GET the subscription for the email on file, create the draft (staging), GET the draft, propose send with the read-back from that GET.
   - `other_email`: log `refused`, say `otherEmail`. If an amount said as money was heard, continue as `one_time_gift` to the email on file, with the same `amountConflict` rule over the turn once the address is set aside. Digits left over from a spoken address are never an amount.
   - `help`, `repeat` (after the proposal it would repeat expired or was set aside, say that nothing is waiting instead), `staff_callback` (log it and say staff will call back during open hours), `goodbye` (end the call), `unclear`.
6. Prepend filtered empathy when present. Log `said` with the text, facts and claims, and for a repeat, `repeats`, the turn whose reply it says again, so the grader proves those claims there. Return `{reply, turn, state, timings: {serverMs, routerMs, paypalMs}}`.

GETs that the reply needs run in parallel (`Promise.all`). `state` for the browser is `{callId, script, verified, locked, ended, pending: {kind, label, expiresAt} | null, record: {subscription, invoice}}` where `record` holds the latest snapshots formatted for display plus their `debugId`. `get(callId)` adds the call's events. `sweep()` ends idle calls and deletes their open drafts.

### check.js

Pure functions over ledger events, shared by the dry run, `pilot-check` and the tests.

- `checkFacts(events, {orgName, subscriptionId})` for each `said` event: every declared fact must equal the value derived from the latest earlier `read` snapshot of its source in the same call, taken only from the call's own subscription (the configured `subscriptionId`, else the first one the call read or proposed a change to), that subscription's plan by its `plan_id`, and the call's own latest draft (or, for a `config.*` source, the config). Every declared fact must be said as whole words, or in words the scans read, such as "twenty five dollars", so "December 1" is never found inside "December 15". Everything the strict scan finds must be covered by a declared fact. Then, with the proven facts, the org name and the allowed phrases set aside, every word left must be in `TEMPLATE_WORDS`, the checked-in list `npm run vocabulary` builds by rendering every exported template in say.js with fixtures, fallback branches included, and stripping their facts the same way. Last, every sentence, with the org name and each proven fact turned into a slot named for its source, must be in `TEMPLATE_SENTENCES`, the checked-in sentences the same build renders, so template words recombined into a new claim, such as "The next gift is this month" or "PayPal no longer shows your monthly gift of {plan.price} as {subscription.status}", fail, and so does the invoice amount put where the gift's amount goes. A reply that says a brace fails (changed Nov 2 after the fourth review). A test fails when either list drifts or a template has no fixture. Then every sentence the templates tie to a claim, in `TEMPLATE_CLAIMS`, must declare it, every declared claim must be its own sentence's and in the reply, and each must be backed by the call's own events up to that reply, or for a repeat, up to the reply it repeats, which its words must end with (changed Nov 2 after the fifth review). Each call is held to the lists it was spoken with: `templatesFor(start)` gives the list the `call_start` names by its `templates` hash in `TEMPLATE_HISTORY`, the current list when it names none, and null when the history lacks it. `templateTrouble(start)` says when a call's list can't vouch for its replies, a list the history lacks or one with a sentence its history entry does not hold as reviewed, and that is a violation, never a pass. With `lenientTemplates`, which pilot-check uses only to tell a refusal from a fail, that trouble is set aside (changed Nov 2 after the sixth review). The org name is the configured `ORG_NAME` in pilot-check, else the one the call logged on `call_start`. Returns the violations.
- `checkWrites(events)`: every `write` has an earlier `yes` in the same call with the same `tokenId`, the `yes` comes from the turn the write ran in, and that turn's `heard` event is the turn right after the matching `proposed` event or later, with `answering` naming the turn before it when logged, `arrivedAfter` naming it too, and `afterReplyMs`, when logged, at least `minAnswerMs`. The proposal was not expired, set aside or declined before the yes, the yes came within `pendingTtlMs` of the proposal and the write within `tokenTtlMs` of the yes, the proposal's read-back came from a read of the write's target, and a sent invoice is a draft the call made. No `write` and no subscription `read` happens before `pin_ok`. Every subscription read, proposal and write in a call targets one subscription id, the configured `subscriptionId` when given.
- `checkSafety(events)`: no invoice read names an email other than the one on file with the call's own subscription, an invoice offered or sent shows its recipient in PayPal's reads, and a locked call reads and writes nothing.
- `checkScript(events, script)`: the call's writes (kinds in order) and staging writes match the script's `expect`, and its final subscription status matches `expect.finalStatus` when set (or equals the starting status when `expect.unchanged` is true). Each proposal reads its amount and status, or the invoice's amount and number, aloud, and each write's reply reads the new status back from PayPal. A script with `expect.readsAloud`, Script 1, needs a reply that declares a fact from each of those sources, its amount and status, so a reply that only says PayPal had no clear answer fails it (changed Nov 2 after the fourth review). Each deleted draft is one the call made, each draft ends sent or deleted, and the final invoice read is of the last draft.
- `medianGap(events, {sources: ['voice']})`, where a reply that never started playing counts as never. `countedGaps(events)` counts the one gap of a turn the line heard from the same source, and a turn with two gaps counts neither. `gapProblems(events)` reports two gaps for one heard turn, and a gap shorter than the line's own logged time for that reply (the `said` event's `ms`), since the reply can't start playing before it exists.
