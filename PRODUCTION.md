Validate backups and runtime role permissions. Then perform a controlled, explicitly authorized low-value live acceptance test and verify settlement and refund behavior in the production account.

## Operation journal contract

The original PostgreSQL adapter reserves mock procurement operations under a unique organization/business key. The separate checkout store freezes the approved sandbox plan and per-vendor create/capture request IDs, commits claims before provider writes and blocks fresh attempts after an unknown result. Confirmed captures require authoritative PayPal order/capture reads. The donor store separately persists calls, audit events and per-action claims when donor durability is enabled; the durable ledger barrier completes before a verified webhook is acknowledged. [The database guide](docs/DATABASE.md) covers explicit administrator migrations and restricted runtime credentials; [commerce setup](docs/COMMERCE.md) describes the sandbox workflow; the current acceptance report above records accepted release evidence.

Production dispatch must supply authenticated organization and donor identity, preserve the same business and provider request IDs across restarts, reconcile unknown attempts from authoritative reads, and advance only from confirmed outcomes. The shared demo organization does not provide production tenant authority, and the legacy local donor mode does not provide the PostgreSQL recovery guarantees.

No environment boolean can replace these requirements. Until they are implemented and validated, keep the sandbox host guard intact.
